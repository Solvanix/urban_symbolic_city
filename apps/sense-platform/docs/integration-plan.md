# خطة التكامل المعمارية لـ SENSE

## القرار المعتمد

تُعد **SENSE Commerce** مصدر الحقيقة الداخلي للمنتجات والخدمات والأسعار والمخزون والطلبات وسجل التدقيق. تعرض المنصة كتالوجها العربي، وتدير السلة والطلب ولوحات الإدارة والمزودين، بينما تبقى بيانات البطاقة وأسرار الدفع لدى شريك الدفع المرخص ولا تُخزن في SENSE.

يرتبط متجر SENSE الداخلي بمتجر الفريق الحالي عبر موصل مزامنة موثق يحدد بوضوح أي نظام يملك كل حقل. لا تُنفذ مزامنة فعلية قبل اعتماد API أو ملف تبادل رسمي من مالك المتجر؛ ولا تُفترض أسماء الحقول أو نقاط النهاية. شركاء النجاح الثلاثة يُعاملون كحدود مستقلة: بوابة الدفع، شركة اللوجستيات، والشريك البرمجي.

يظل **Senseivo** موقع الهوية والفريق والمحتوى المؤسسي. يرتبط بالمنصة عبر روابط وهوية بصرية مشتركة، لكنه لا يصبح لوحة تشغيل أو مصدرًا لحالات البلاغات والطلبات. مسارات التشغيل والحسابات والصلاحيات تبقى داخل SENSE.

## حدود التكامل المستهدفة

| المجال | مصدر الحقيقة | ما تنفذه SENSE | الحالة |
|---|---|---|---|
| المنتجات والخدمات | SENSE Commerce مع مزامنة اختيارية من متجر الفريق | كتالوج داخلي، مراجعة مزود، نشر وإخفاء | قيد التنفيذ |
| الأسعار والمخزون | SENSE Commerce بعد اعتماد سياسة المزامنة | حماية من البيع فوق المخزون وسجل تغييرات | قيد التصميم |
| السلة والطلب | قاعدة SENSE | إنشاء طلب داخلي برقم مرجعي وحالة قابلة للتدقيق | قيد التنفيذ |
| الدفع | شريك دفع خارجي | إنشاء جلسة دفع، استقبال نتيجة موقعة، حفظ مرجع غير حساس فقط | ينتظر بيانات الشريك |
| الشحن والتنفيذ | شريك لوجستي خارجي | إنشاء شحنة، رقم تتبع، وتحديثات Webhook موقعة | ينتظر بيانات الشريك |
| المتجر الحالي | موصل API أو تبادل ملفات يعتمد رسميًا | مزامنة معلنة الاتجاه والحقول وسياسة التعارض | ينتظر مواصفات المالك |
| الشريك البرمجي | عقد تكامل أو خدمة وسيطة يوافق عليها الفريق | تحويل العقود، المراقبة، وإعادة المحاولة دون كشف أسرار | ينتظر نطاق العمل |
| الهوية المؤسسية | Senseivo | رابط وهوية مشتركة وصفحات معلومات | قرار معماري |
| البلاغات والصلاحيات | قاعدة SENSE | tRPC وحواجز الأدوار وسجل الأحداث | موصول ومختبر |

## عقود التكامل الإلزامية

كل موصل خارجي يجب أن يحدد عنوان البيئة، الإصدار، طريقة المصادقة، مهلة الطلب، سياسة إعادة المحاولة، معرفًا idempotency، توقيع Webhook، وحالات الخطأ. تُحفظ الأسرار في إعدادات البيئة أو مدير أسرار المنصة، ولا تُكتب في المستودع أو المحادثة أو سجلات الطلبات.

يجب أن تكون Webhooks قابلة للتحقق وإعادة التشغيل الآمن. يحفظ النظام الحد الأدنى من البيانات: المعرف الخارجي، نوع الحدث، وقت الاستقبال، بصمة الحدث، نتيجة المعالجة، وعدد المحاولات. تُمنع معالجة الحدث مرتين عبر قيد idempotency وسجل تدقيق.

## سياسة المزامنة مع متجر الفريق

قبل بناء الموصل، يقدم مالك المتجر مواصفة مكتوبة تتضمن: النظام المصدر لكل حقل، معرف المنتج المشترك، الحقول القابلة للتعديل من SENSE، الحقول التي تبقى مملوكة للمتجر الحالي، تكرار أو Trigger المزامنة، سياسة تعارض الأسعار والمخزون، وآلية حذف أو إخفاء المنتج. إذا لم تتوفر هذه المواصفة، يعمل الكتالوج الداخلي ببيانات يديرها المزود أو المدير داخل SENSE فقط.

## ما لن تُخزنه SENSE

لا تُخزن أرقام البطاقات أو CVV أو رموز المصادقة الخاصة بالدفع. لا تُخزن كلمات مرور الشركاء أو مفاتيح API في قاعدة البيانات أو GitHub. لا تُعرض حالة دفع أو شحن على أنها نهائية قبل وصول حدث موثق من الشريك المعني.

## التدرج التنفيذي

يبدأ التنفيذ بكتالوج داخلي ومنتجات مزودين معتمدين، ثم تُضاف الطلبات الداخلية وحالاتها، وبعدها موصل الدفع، ثم موصل اللوجستيات، ثم مزامنة متجر الفريق، وأخيرًا واجهة الشريك البرمجي إن لزم. كل مرحلة تحتاج اختبارات عقد واختبارات صلاحيات وسجل تدقيق قبل تفعيلها للمستخدمين.
