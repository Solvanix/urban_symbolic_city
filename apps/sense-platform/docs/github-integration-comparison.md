# مقارنة Urban Symbolic City وSENSE وقرار الدمج

## الغرض

هذا المستند يحدد الفرق بين مستودع `Solvanix/urban_symbolic_city` ومشروع `sense-urban-platform`، ويمنع استبدال محتوى المستودع الأصلي أو نقل عناصر غير موثقة قبل اعتماد بنية واضحة.

## نتيجة التدقيق

مستودع Urban Symbolic City عام، ويحتوي على موقع HTML/CSS/JavaScript ومجموعة صفحات وواجهات ونماذج تخطيطية مرتبطة بالمدينة الذكية والاستدامة والذكاء الاصطناعي الرمزي والتواصل الصوتي وبعض أفكار التطبيقات. أحدث نسخة تمت معاينتها هي commit `8982441` بتاريخ 2026-06-01، ويحتوي المستودع على فرع `main` وقرابة 43 ملفًا في النسخة المحلية المستنسخة، من بينها 25 صفحة HTML و3 ملفات JavaScript وملف CSS رئيسي.

مشروع SENSE هو تطبيق React 19 وVite وTailwind 4 وExpress وtRPC وDrizzle وVitest، مع مصادقة Manus وكتالوج تجارة داخلي قابل لموصلات الشركاء. يحتوي على بنية تطبيق قابلة للتوسع، صفحات عامة مترابطة، سلة وCheckout داخلي، وملف تفضيلات وصول محلي، إضافة إلى دورة البلاغات ولوحات الأدوار والإشعارات والمؤشرات.

## قرار الدمج

القرار المقترح هو **دمج محافظ متعدد الطبقات** وليس نسخ مشروع SENSE فوق المستودع الأصلي. يبقى `urban_symbolic_city` هو المستودع الرئيسي الذي يحفظ تاريخ المشروع الأصلي وموقع المظلة والمحتوى المعرفي. تُضاف منصة SENSE داخله كتطبيق رئيسي منظم في مسار واضح مثل `apps/sense-platform/` أو `platform/`، مع إبقاء الموقع الثابت الحالي في جذره إلى أن تتم مراجعة قرار النشر.

لا يجوز حذف `index.html` أو `assets/` أو `interfaces/` أو `projects/` أو `symbolic_impact_analysis/` لمجرد إضافة SENSE. كما لا يجوز دمج `node_modules` أو الأسرار أو ملفات `.env` أو مخرجات البناء أو بيانات الشركاء التجارية الخاصة داخل GitHub.

## ما سيتم اعتماده من كل طرف

من Urban Symbolic City سيتم اعتماد الاسم والمظلة والرؤية الحضرية والاستدامة والمواد التعليمية والخطط والتحليلات التي تثبت فائدتها، إضافة إلى الأفكار الخاصة بالرسائل الرمزية والصوت والواجهات الحضرية. ستُراجع هذه المواد لغويًا وتقنيًا، ويُوسم كل عنصر بوضوح: `concept` أو `prototype` أو `verified`، حتى لا يُعرض النموذج الأولي باعتباره خدمة تشغيلية.

من SENSE سيتم اعتماد المكدس البرمجي، الهوية Blueprint، RTL، صفحات السياحة والخدمات والمتجر الداخلي، CartProvider، نظام التفضيلات المحلي، الاختبارات، ثم تُبنى داخل المسار الجديد النواة التشغيلية للبلاغات والأدوار والخرائط والإشعارات والقياس والمالية وفق الخطة المتبقية.

## ما لا يجب دمجه تلقائيًا

لا تُدمج ملفات HTML الثابتة داخل مسارات React دون تحويل واعٍ للروابط والهوية والوصول. ولا تُعلن تطبيقات أو نماذج AI أو خدمات صوتية كميزات مكتملة لمجرد وجود ملف HTML أو زر في JavaScript. كذلك لا تُنقل أي بيانات اتصال أو أسرار أو بيانات شخصية أو بيانات تجارية خاصة بالشركاء إلى مستودع عام.

## استراتيجية النقل

المرحلة الأولى هي إنشاء نسخة عمل محلية للمستودع الأصلي، ثم إضافة مشروع SENSE داخل مسار مستقل، وتوثيق نقطة الدخول والتشغيل والروابط. المرحلة الثانية هي نقل المواد المعرفية والواجهات المنتقاة، لا نسخ كل الملفات بلا مراجعة. المرحلة الثالثة هي اختبار البناء والروابط وRTL وعدم تعارض GitHub Pages مع خادم SENSE. المرحلة الرابعة هي إنشاء commit واضح، ثم عرض قائمة الملفات والاختبارات قبل طلب تأكيد الدفع إلى GitHub الخارجي.

لا يتم تنفيذ `push` إلى GitHub الخارجي قبل موافقة صريحة على نتيجة المقارنة وخطة الدمج، لأن الدفع سيغير مستودعًا عامًا مملوكًا للمستخدم.
