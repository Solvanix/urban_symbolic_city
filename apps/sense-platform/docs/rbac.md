# مصفوفة الصلاحيات في SENSE

هذه الوثيقة تصف الحماية الفعلية في الخادم، ولا تعتبر إخفاء رابط في الواجهة بديلًا عن التحقق داخل إجراء tRPC.

| النطاق | المواطن | الموظف | الميداني | المشرف | المدير | عضو مزود الخدمة |
|---|---|---|---|---|---|---|
| إنشاء بلاغ وعرض بلاغاته وتقييم البلاغ المغلق | نعم، للحساب نفسه | لا | لا | لا | لا | لا |
| طابور البلاغات | لا | حالات المراجعة وإعادة الفتح | البلاغات المسندة إلى الحساب | الاعتماد وإعادة الفتح | المجموعة التشغيلية الكاملة | لا |
| تغيير حالة البلاغ | لا | المراجعة والإسناد والتحويلات المسموحة | التنفيذ والاعتماد الميداني للبلاغ المسند | الاعتماد والإغلاق | كل التحولات المسموحة | لا |
| رفع دليل ميداني | لا | لا | للبلاغ المسند إلى الحساب | نعم | نعم | لا |
| البلاغات القريبة | لا | بحسب طابور الدور | بحسب البلاغات المسندة | نطاق الاعتماد | النطاق التشغيلي الكامل | لا |
| مؤشرات التشغيل | لا | لا | لا | نعم | نعم | لا |
| كتالوج المزود ومحتواه | لا | لا | لا | لا | مراجعة واعتماد إداري | بحسب دور العضو داخل مزوده |
| بيانات الدفع المرجعية للمزود | لا | لا | لا | لا | مراجعة إدارية دون تخزين بيانات بطاقة | owner/manager/finance_viewer وفق الإجراء |

## قواعد التنفيذ

تستخدم إجراءات البيانات المصادق عليها `protectedProcedure`، ثم تطبق تحققًا إضافيًا حسب الدور وملكية السجل. لا يعتمد النظام على قيمة يرسلها العميل لتحديد هوية المواطن أو نطاقه. ويُحصر رفع الأدلة في أدوار التشغيل المخولة، مع فحص نوع الملف وحجمه وملكية البلاغ قبل التخزين.

تستخدم دورة البلاغات سياسة انتقال نقية في `server/reportWorkflow.ts`، بحيث يُرفض الانتقال غير الموجود في مخطط الحالات أو غير المسموح للدور. كما يُمنع الدور الميداني من العمل على بلاغ غير مسند إليه، ويُقصر الإغلاق على المشرف والمدير.

تُفصل صلاحيات أعضاء المزود في `server/providerAccess.ts` عن أدوار البلدية. يملك `owner` و`manager` إدارة الملف والأعضاء، ويملك `editor` إدارة المحتوى دون الاطلاع المالي، بينما يملك `finance_viewer` الاطلاع المالي المرجعي دون تعديل المحتوى.

## حدود معروفة

تظل المقاييس المرتبطة بحوادث الصلاحيات أو الإسناد الخاطئ غير متاحة حتى تتوفر سجلات تشغيل صريحة لها. لا تُستخدم أرقام تقديرية أو بيانات تجريبية لسد هذا النقص. كما أن صلاحيات Shopify لإدارة الطلبات النهائية تبقى داخل Shopify إلى أن يُفعل تكامل موثوق عبر Admin API أو Webhooks.

## سجل الإجراءات الحساسة

| الإجراء | الحماية | القيد الإضافي |
|---|---|---|
| `reports.create`, `reports.mine`, `reports.rating`, `reports.rate` | حساب مصادق | هوية المواطن وملكية البلاغ، والتقييم للبلاغ المغلق فقط |
| `reports.queue`, `reports.nearby`, `reports.transition` | حساب مصادق + دور تشغيلي | ترشيح الطابور حسب الدور وسياسة الانتقال والإسناد |
| `reports.kpis` | مشرف أو مدير | مؤشرات من السجلات الحقيقية مع مرشحات فترة وتصنيف |
| `reports.byId` | حساب مصادق + ملكية أو دور تشغيلي | المواطن يرى بلاغه، والميداني بلاغه المسند، والتشغيل وفق الدور |
| `reports.uploadEvidence` | ميداني أو مشرف أو مدير | فحص نوع وحجم الملف، وملكية الإسناد للدور الميداني |
| `commerce.checkout.recordHandoff`, `commerce.checkout.mine` | حساب مصادق | ربط الإحالة بالمستخدم وعدم تخزين بيانات الدفع |
| `notifications.mine`, `notifications.markRead`, `notifications.markAllRead` | حساب مصادق | عزل الإشعار بحسب `userId` |
| `ai.classifyReport` | حساب مصادق | النص منقح من البيانات الشخصية والنتيجة اقتراح غير ملزم |
| `providers.*` الإدارية | حساب مصادق | عضوية المزود ودور العضو أو صلاحية المدير الإداري |
| `providers.adminReviewQueue`, `providers.adminReview` | مدير | مراجعة الاعتماد وسجل التدقيق |

يُحفظ هذا السجل البرمجي في `server/rbacManifest.ts` ويُختبر للتأكد من عدم حذف إجراء حساس من التوثيق عند إضافة موجه جديد. هذا السجل لا يستبدل حراس الخادم؛ بل يجعل عقد الحماية قابلًا للمراجعة الآلية والبشرية.
